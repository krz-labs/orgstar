Source blocks

A source block holds code in a named language:

#+begin_src python
return 6 * 7
#+end_src

orgstar reads the same syntax Org does: the language after #+begin_src, then any switches such as -i or -r, then header arguments. A #+NAME: line above a block names it, so other blocks, #+CALL: lines and :var references can refer to it.

Lines inside a block that start with * or #+ are protected with a leading comma, as Org does (org-escape-code-in-region). The comma is removed when the block runs, tangles or exports, and when you edit the block apart.

Editing a block apart

org-edit-special edits a block's contents in a separate editor. Put the caret in a src, example or export block (or on a #+TBLFM: line; see Tables) and run Edit Block.

PresetKey
EmacsC-c '
DoomC-c ', or SPC m ' in normal state
Mac⌃⌘'

On the Mac the block opens in a sheet titled with the block's kind and language, with the same highlighting as the main editor. The protecting commas are removed while you edit and added back when you save.

ActionKeys
SaveC-c ' or ⌘Return, or Save Block
LeaveC-c C-k or Escape, or Cancel

If the block changed in the main editor while you edited it, the edit is not saved and the message area says so.

On iOS the block opens in a plain text sheet with Cancel and Save buttons.

Running a block

C-c C-c in a source block runs it (org-babel-execute-src-block) and writes its result under it. The same command runs a #+CALL: line or an inline src_ block when the caret is on one.

PresetKey
EmacsC-c C-c
DoomC-c C-c in normal, insert and visual state
Mac⌃⌘X

The program runs in the folder of the file, or in :dir. It reads the code on standard input. While it runs, the message area shows "Running language block…"; when it ends, it shows "Code block evaluation complete." or the problem.

If the program writes to standard error or exits with a non-zero status, the message area shows the exit status and the first line of standard error. The result is still inserted, as Emacs does.

The block's text is remembered when the run starts. If you edit the block while it runs, so it can no longer be found, the result is not written.

Languages that run

On the Mac, orgstar starts each interpreter outside a :session through /bin/sh, as Org does, with standard input read from a file. Because an app opened from the Dock does not see your shell's PATH, orgstar adds /opt/homebrew/bin, /usr/local/bin, /Library/TeX/texbin, /usr/bin and /bin to the end of it.

LanguageProgram run
sh, bash, zsh, fish, ksh, dash, ash, csh, mksh, poshThe shell of that name
shellThe shell in SHELL, or /bin/sh
pythonpython3, or the program in :python
emacs-lisp, elispemacs -Q --batch, or the interpreter; see below
rubyruby, or the program in :ruby
js, javascriptnode FILE, the program written to a file, or WebKit without node; see below

For js, javascript and R, :cmd names a different program. Since it runs through /bin/sh, a program in :cmd, :python or :ruby can be given with options, such as :cmd "node --no-warnings" or :python "python3 -X utf8", or with ~ or a variable, such as :cmd "~/bin/node". awk takes :cmd-line arguments after its program, and :in-file as the file it reads.

Any other language is refused with "No way to run language blocks yet."

A run that takes longer than five minutes is stopped. Runs in a :session have no time limit, except JavaScript in WebKit and Python in Pyodide.

The Mac App Store version starts no programs, so only Emacs Lisp, JavaScript, Python, calc, sqlite, dot and mermaid blocks run there; see In the Mac App Store version below.

JavaScript in WebKit

In the Mac App Store version and on iOS, js and javascript blocks run in a web worker of a hidden WebKit web view, with JavaScriptCore, the JavaScript engine built into macOS and iOS. The download version uses it when node, or the program in :cmd after /bin/sh expands it, isn't installed; a :cmd with options, such as node --no-warnings, or with a command substitution, such as $(which node), never runs in WebKit. A block runs as Emacs runs it, with node reading it from a file as a CommonJS module, where this is module.exports and top-level var declarations stay in the block. Its output and result are what node gives:

  • console.log, console.info and console.debug write to the output, console.warn and console.error to the error output, and console.dir prints with util.inspect. process.stdout.write and process.stderr.write write text.
  • require('util') has inspect, format and formatWithOptions, which print values as Node 26 prints them. require('process') has stdout and stderr.
  • setTimeout, setInterval, their clear functions and queueMicrotask work. Timers run after the program, in the order node runs them, and the run ends when none is left. In a :session, a block that leaves a timer set, or whose promise callbacks print or throw, is refused, since node's session returns before they run and they print later.
  • fetch, XMLHttpRequest and WebSocket reach the network, as they do in a web page, and the run waits for a request or an open socket to end, as node does. To read a response from another site, the server must allow it (CORS). In a :session, a block can't wait, so starting a request there is refused; a synchronous XMLHttpRequest works.
  • An uncaught error ends the run with status 1 and writes its name and message to the error output, such as "ReferenceError: hline is not defined".
  • require of any other module fails as it does for a module node can't find: "Error: Cannot find module 'fs'".

A block that uses something only node has fails with "This block uses name, which runs only in node.", rather than giving a different result. That covers other members of process, util, console, require and module (process.env, console.table, require.resolve, module.id) and listing their members; Node's other globals (Buffer, URL, TextEncoder, setImmediate, structuredClone, SharedArrayBuffer, Temporal, ReadableStream); top-level await, import or export statements, which node runs as an ES module, and import(); __filename and __dirname, which name Emacs's temporary file; listing the global object's properties with Object.getOwnPropertyNames or Reflect.ownKeys, and in a :session with Object.keys or for…in; the source text of a built-in function; an error's stack, Error.stackTraceLimit, Error.captureStackTrace and listing an error's own properties; and printing an Error, a Promise, an iterator or the global object with util.inspect, whose text in node comes from its own engine. There is no access to files or other programs.

Some things still differ from node:

  • Error messages written by the engine itself, such as a TypeError's, are JavaScriptCore's, as a block that prints e.message shows. Only an uncaught ReferenceError is written in node's words.
  • A promise rejection nothing handles is not reported, and the run does not stop for it.
  • The web worker's own globals, such as self, importScripts and XMLHttpRequest, are there too.
  • In a :session, a block's top-level declarations carry over to later blocks, but var and function declarations don't become properties of the global object.
  • :cmd is ignored.

Each block without a session runs in a new worker, and each session in a worker of its own. A block that is canceled, or that runs for five minutes, a program that never finishes included, is stopped at once with its worker; for a block in a :session, that ends the session. The web view is unloaded after a minute without a JavaScript block, or 15 minutes while a session exists, which ends every session.

Python in Pyodide

In the Mac App Store version and on iOS, python blocks run in Pyodide 314.0.8, which is CPython 3.14 compiled to WebAssembly, built into the app and run in a hidden web view. The download version always runs python3. A block runs as Emacs runs it with python3, with the same results, output and error output: the body as a function whose return value is the result, or with :results output what it prints, and with :session at top level, where the value is the last expression's. An uncaught error writes its traceback to the error output; outside a session the run ends with status 1, as python3 does.

What differs from python3:

  • Only the standard library is there. numpy, matplotlib and other packages are not, and orgstar doesn't install them: import numpy fails with ModuleNotFoundError. Loading a package from the network with pyodide_js.loadPackage and its URL works, but isn't supported. A block with :results graphics fails with "Python blocks can't draw graphics in this version of orgstar: matplotlib isn't included." A :file result that is the block's value or output is written as for any other language.
  • The block can reach the network, as a web page can: urllib.request, js.fetch and pyodide.http work.
  • The block can't see your files or start programs. It runs in Pyodide's own file system, in /home/pyodide, and files it writes there are not kept. :dir must name a folder that exists, but the block doesn't run in it. input() reads nothing.
  • :python is ignored.
  • Every block runs in one interpreter. A block without a session gets its own variables, but modules it imports stay loaded, with any changes it made to them, until Pyodide is unloaded. A session keeps its variables until then too.
  • Pyodide loads with the first python block, which takes a second or two, and is unloaded after a minute without a python block, or 15 minutes while a session has variables. A block that is canceled, or stopped after five minutes, stops at once and ends every session.

Compiled languages

On the Mac, C, C++, cpp, D, java, fortran and clojure blocks run as Org's ob-C, ob-java, ob-fortran and ob-clojure run them. orgstar writes the body, expanded as tangling writes it (see Tangling below), to a source file in a temporary folder, compiles it and runs the program in the file's folder or :dir, with a newline on standard input. What the compiler prints is dropped.

LanguageCommands
Cgcc -o bin FLAGS src LIBS, then bin CMDLINE
C++, cppg++ -o bin FLAGS src LIBS, then bin CMDLINE
Drdmd FLAGS src CMDLINE, which compiles and runs

javajavac CMPFLAG Class.java, then java -cp dir CMDLINE Class CMDARGS

When :imports is absent, a D block reads the IMPORTS property where it is, and a Fortran block without :includes or :defines reads the INCLUDES and DEFINES properties, as Org does when it runs them. :session is ignored for these languages, as in Org.

Java's defaults are :results output and :dir . (org-babel-default-header-args:java). The .java and .class files are written in the folder the block runs in, under folders for the class's package (org/ex/Hello.java for :classname org.ex.Hello), and are left there. The class is :classname, the body's own class with its package, or Main.

Any other Clojure backend is refused: "The cider backend for clojure needs Emacs; orgstar runs babashka or clojure-cli."

Before a run, orgstar checks that each program it needs is on the PATH described above. If not, the block fails with "gcc isn't installed, so C blocks can't run." (g++ for C++, rdmd, gfortran, or the commands :javac and :java name). For Clojure without a :backend, the message is "Neither bb nor clojure is installed, so clojure blocks can't run."

The trust prompt

Before a block runs, orgstar asks "Run this language block? (yes, no, always)", as org-confirm-babel-evaluate does.

  • yes runs it this once.
  • no does not run it.
  • always runs it and remembers the block, so it runs without asking next time.

A remembered block is identified by the file's path and the exact text of the block. Any change to the block, or moving the file, makes orgstar ask again. The remembered hashes are kept in trusted.json in orgstar's Application Support folder (~/Library/Application Support/Orgstar on the Mac, inside the container in the Mac App Store version). The same file records table formulas you allowed to run Lisp. To forget every choice, delete the file while orgstar is not running.

When a block's :var or :stdin refers to other blocks that have to run first, you are asked once for all of them. The prompt covers the block you ran and every block its references reach. If any of those blocks changes while the chain runs, orgstar stops with "The blocks changed while running; nothing more was run."

:eval

ValueEffect
never, noThe block does not run: "Evaluation of this language code block is disabled."
queryAsks every time, with only yes and no. A block reached through :var with :eval query makes the whole chain ask every time.
anything else, or absentRuns after the trust prompt.

never-export and no-export only stop evaluation during export in Org. orgstar does not run blocks during export, so with these values the block runs from C-c C-c like any other.

Cancelling a run

On the Mac, Edit ▸ Cancel Running Task (⌘.) stops the running block. Its result is not inserted, and the message area shows "Code block canceled." The same command stops an export or table recalculation running in Emacs (see Export and Tables). With nothing running it shows "Nothing is running". The command is also in the command palette.

Only one block runs at a time. Starting another block cancels the one that is running.

Cancelling a block that runs in a :session stops the session's interpreter, so the session's state is lost. The next block in that session starts a new one.

The iOS app has no cancel command.

Results

The result is written after a #+RESULTS: line below the block (org-babel-insert-result). Running again replaces it. A named block's result goes under #+RESULTS: name, wherever that line is in the file. An unnamed block's result is the #+RESULTS: line right after it, past blank lines. The result keeps the block's indentation, so a block inside a list item keeps its result inside the item.

#+begin_src sh
echo hello
#+end_src

#+RESULTS:
: hello

By default a result is shaped like this:

  • Text of fewer than ten lines gets a =: = prefix on each line.
  • Text of ten lines or more goes in an #+begin_example block.
  • A table becomes an aligned Org table.

Results in files

With :results file, the result is a link instead of text.

HeaderEffect
:file nameWrite the result into name and link to it. Without :results file, :file has no effect, except in graphics blocks.

#+end_src

#+RESULTS:
[[file:out.txt][Output]]

Header arguments

Where they come from

orgstar merges header arguments in this order, each layer overriding the ones before it (org-babel-get-src-block-info):

  1. #+PROPERTY: header-args … in the file, then header-args properties of the block's headings, from the outermost heading inwards.
  2. header-args:LANG the same way, for blocks in language LANG.
  3. The arguments on the #+begin_src line.
  4. #+HEADER: lines above the block.
  5. For a call, the call's arguments (see Calls below).

A property written with a +, such as header-args+, adds to the value inherited from above instead of replacing it. In a property drawer, :header-args:sh: is one property name, so its value applies only to sh blocks.

#+PROPERTY: header-args :results output

* Scripts
:PROPERTIES:
:header-args:sh: :dir /tmp
:END:

#+HEADER: :results verbatim
#+begin_src sh :var name="world"
echo "hello $name"
#+end_src

Without any of these, a block has :results replace, :exports code, :session none, :cache no, :noweb no, :hlines no and :tangle no. An inline src_ block defaults to :exports results and :hlines yes.

Lisp in header values

A header value that starts with (, ', ` or [ and is not in quotes is Lisp, as in org-babel-read. orgstar evaluates it with its own Emacs Lisp interpreter, which also knows buffer-file-name, default-directory, system-type and the functions expand-file-name, file-name-directory, file-name-nondirectory, file-name-sans-extension and file-name-as-directory.

#+begin_src sh :dir (concat "/" "usr") :results output
pwd
#+end_src

A string or number takes the place of the form. Lisp that the interpreter cannot evaluate is refused where it matters: for :var ("is Lisp that only Emacs can evaluate"), :colnames and :rownames, and any header of a :cache yes block.

Variables

:var name=value passes a value into the block (org-babel-ref-resolve). One :var can hold several assignments separated by spaces, and you can repeat :var. A later assignment to the same name replaces an earlier one.

ValueMeaning
5, 2.5A number.

'(1 2), (+ 1 2), '((1 2) hline (3 4))Lisp: evaluated to a string, number, list or table.

#+NAME: nums
| 1 | 2 |
| 3 | 4 |

#+begin_src python :var t=nums :var scale=10
return [[c * scale for c in row] for row in t]
#+end_src

A referenced block runs before the block that refers to it, after the one trust prompt that covers them all. A block with :cache yes and a current result gives that result without running. A chain that leads back to itself is refused with "name refers to itself through :var"; a chain through :post or a noweb reference names that instead.

A referenced block with :results file gives the name of its :file, or without :file its result as text. The file is written when the block runs.

These are not supported and are refused:

  • Indexing into a table, such as tbl[1,2]: "References like … aren't supported yet."
  • A name that matches nothing in the file: "Can't find … for :var."
  • References to other files.

Tables in variables

A table passed as a variable loses some of its structure first (org-babel-disassemble-tables):

  • Rules are removed, unless :hlines yes.
  • The first row is taken off as column names when :colnames yes, or when the table's only rule is under the first row. :colnames no keeps it as data.
  • The first column is taken off as row names when :rownames yes.

If the result is a table of the same width (for columns) or height (for rows), the names are put back on it (org-babel-reassemble-table). Clojure results don't get them back, as in Org. :colnames and :rownames can also be Lisp lists of names to put on the result, such as :colnames '("x" "y").

#+NAME: tbl
| a | b |
|---+---|
| 1 | x |
| 2 | y |

#+begin_src python :var t=tbl
return [r + ["!"] for r in t]
#+end_src

Standard input and arguments

For shell blocks, :stdin name sends a table, list or block result to standard input, a table as tab-separated lines. :cmdline gives the script arguments, and :shebang its first line. With any of the three, the block is written to an executable script and run by the shell (org-babel-sh-evaluate); without :shebang, the first line is #!/usr/bin/env and the shell's name. A block with :stdin or :cmdline runs as a script even with a :session, and leaves the session untouched; :shebang alone runs in the session.

#+begin_src sh :cmdline one "two words" :results output
for a in "$@"; do echo "[$a]"; done
#+end_src

Sessions

:session name runs the block in an interpreter that stays running, so variables, functions and the working folder carry over to the next block in the same session. Sessions work for shells, Python, Ruby, JavaScript (Node, or JavaScriptCore) and R in the Mac download version, and for JavaScript and Python (in Pyodide) on iOS and in the Mac App Store version.

  • :session with no name uses *language*, such as *sh*. :session none runs without one.
  • A session belongs to one folder, one interpreter and one name. Blocks in different folders, or with different names, do not share state.
  • A session starts in the block's :dir, or the file's folder, the first time it is used.
  • A shell session's output is what the block prints. :results value gives the exit status of the last command.
  • A Python session runs the block at top level. Its value is the value of the last expression, so return is not used.
  • A Ruby session runs each block in the same binding, and a JavaScript session in Node's global context or one web worker, so local variables and var and let declarations carry over. Their value is the value of the last expression, written as without a session (inspect, util.inspect); return is not used. Errors go to the block's error output and leave the session running.
  • An R session runs each block with source(…, print.eval = TRUE) in one R --slave process; its result is the output, as without a session.

Emacs runs these with packages beyond Org: inf-ruby for Ruby, ESS for R, and js-comint or skewer for JavaScript; with plain node, ob-js refuses sessions. orgstar's sessions don't need them, and their results can differ in detail from those packages' echoed output.

  • Sessions stop when you quit orgstar, or when you cancel a block running in one.
#+begin_src python :session py :results output
a = 2
print("set")
#+end_src

#+begin_src python :session py
a * 3
#+end_src

Caching

With :cache yes, orgstar computes a SHA-1 hash of the block's header arguments and expanded body, as org-babel-sha1-hash does, and writes it on the results line: #+RESULTS[hash]:. When you run the block again and the hash matches, nothing runs and the message area shows the cached value ("Cached: …").

Change the block or its arguments and it runs again. Results inserted with append or prepend carry no hash. Inline blocks are not cached. A cached block that has Lisp in its header arguments the interpreter cannot evaluate is refused.

The hash of a C, C++, D, Java, Fortran or Clojure block is taken over the body as the language expands it (see Tangling below), with the IMPORTS, INCLUDES and DEFINES properties where the block is, and Java's default header arguments, as Emacs does. A result Emacs wrote for such a block with :cache yes is recognised as current, and C-c C-c shows it.

Post-processing

:post names a reference that is resolved after the block has run (org-babel-execute-src-block). The block's result is bound to *this*, and the value of the reference becomes the block's result. The reference is usually a call to a named block that takes *this* as an argument; it can pass other arguments as well.

#+NAME: total
#+begin_src emacs-lisp :var rows='()
(append rows (list 'hline (list "sum" (apply #'+ (mapcar #'cadr rows)))))
#+end_src

#+begin_src sh :post total(rows=*this*)
printf 'a 1\nb 2\n'
#+end_src

#+RESULTS:
| a   | 1 |
| b   | 2 |
|-----+---|
| sum | 3 |
  • *this* is the result as a :var would get it: a string, a number or a table.
  • With :results file and :file, the file is written first and *this* is the link to it, with its :file-desc. The value of the reference then goes in as text, not as a link; use :results drawer or raw when it is Org markup, such as an #+ATTR_ line above the link. With :results file and no :file, *this* is the result as text, and the value of the reference becomes the link.
  • The value is inserted according to the block's own :results.
  • The block that :post calls can have its own :post, and :var references in it can use *this*.
  • With :cache yes and a current result, neither the block nor the reference runs.
  • #+CALL: lines, inline calls and inline source blocks take :post too.

The one trust prompt covers the block and every block the reference runs, and asks every time when any of them has :eval query. Before anything runs, orgstar resolves the reference with an empty *this*; when that fails, the message says why and nothing runs. That covers a name that isn't a block in the file, a block with :eval never, a language orgstar can't run, and a reference that leads back to its own block ("name refers to itself through :post").

Noweb

A noweb reference <<name>> in a block's body stands for other code. Whether references expand depends on :noweb and on what is happening:

:nowebRunningTanglingExporting
no (default)nonono
yesexpandsexpandsno
tanglenoexpandsno

no-exportexpandsexpandsno
strip-exportexpandsexpandsno
strip-tangleexpandsremoves the referencesno

Exported code always shows the references as written; see Export.

<<name>> expands to the first of these that exists:

  1. The contents of the heading whose ID property is name, or whose CUSTOM_ID is name without its leading #.
  2. The body of the source block named name.
  3. The bodies of all blocks with :noweb-ref name, joined by each block's :noweb-sep (a newline by default).

Blocks under a COMMENT heading are skipped. A referenced block expands its own references according to its own :noweb, up to 32 levels deep.

Text before the reference on its line is repeated before each line the reference brings in, so references inside comments or indented code keep their prefix. :noweb-prefix no turns this off.

#+NAME: greeting
#+begin_src sh
echo hello
#+end_src

#+begin_src sh :noweb yes
<<greeting>>
echo world
#+end_src

References that run a block

<<name()>> stands for the result of the block named name, which runs first, and <<name(arg=value)>> runs it with arguments, as :var x=name(arg=value) does (org-babel-ref-resolve). A result that is a string goes in as it is; a number, list or table goes in as Emacs Lisp prints it, such as 42 or ((1 2) (3 4)). Text before the reference is repeated before each line of a result of several lines, unless :noweb-prefix no.

#+NAME: port
#+begin_src emacs-lisp :var base=8000
(+ base 80)
#+end_src

#+begin_src sh :noweb yes
echo "listening on <<port(base=3000)>>"
#+end_src

#+RESULTS:
: listening on 3080

These references expand when the others do for running: with :noweb yes, eval, no-export, strip-export or strip-tangle. With no or tangle, the text stays as written and nothing runs. A block brought in by <<name>> has its own references run in the same way, according to its own :noweb.

The rules for :var references apply: one trust prompt covers every block that would run, a referenced block with :cache yes and a current result gives that result without running, :eval never on a referenced block stops the run, and a reference that leads back to its own block is refused with "name refers to itself through a noweb reference".

Export shows these references as written and runs nothing. Tangling does not run blocks; see What tangling refuses below.

Calls

#+CALL: lines

#+CALL: runs a named block with other arguments, as Org's library of Babel calls do (org-babel-lob-get-info). Run it with C-c C-c on the line.

#+NAME: double
#+begin_src sh :var n=2
echo $((n*2))
#+end_src

#+CALL: double(n=5)

#+RESULTS:
: 10

The full form is #+CALL: name[inside](arguments) end:

  • name is the block to run. It must be in the same file.
  • [inside] holds header arguments applied to the block, such as [:results raw].
  • (arguments) are :var assignments, separated by commas.
  • end holds header arguments for the call's result, such as :results verbatim.

The call also takes the header-args and header-args:LANG properties, and #+PROPERTY: lines, where the call is, with LANG the called block's language. They apply after the called block's own header arguments and before [inside], as in Org.

The result goes under the call. A #+NAME: line above the #+CALL: names the result.

Inline calls and blocks

An inline source block, src_sh{echo hi}, runs with C-c C-c on it. Header arguments go in brackets: src_sh[:var x=3]{echo $x}. The result is written right after the block as a results macro:

Text src_sh{echo hi} {{{results(=hi=)}}} end.

Running again replaces the macro. With :results raw the result goes in as it is, without the macro. An inline result must be one line, and a table result must be a single cell.

An inline call, call_double(n=6), has the same parts as a #+CALL: line: call_name[inside](arguments)[end]. C-c C-c on an inline call runs it, and its result is written after it as a results macro, as for inline blocks. It takes the properties where it is as a #+CALL: line does.

Emacs Lisp blocks

On the Mac, an emacs-lisp or elisp block runs in a new emacs -Q --batch for each run, with lexical binding on. -Q means your init file and packages are not loaded, and nothing carries over between runs. orgstar looks for Emacs at ORGSTAR_EMACS, then /opt/homebrew/bin/emacs, /usr/local/bin/emacs, /Applications/Emacs.app/Contents/MacOS/Emacs, /run/current-system/sw/bin/emacs and /usr/bin/emacs. Without Emacs, the block runs in orgstar's own Emacs Lisp interpreter, and a block that uses something the interpreter does not have fails with "This block uses Emacs Lisp that runs only in Emacs, and Emacs isn't installed."

On iOS, Emacs Lisp blocks run in orgstar's own Emacs Lisp interpreter. It has the forms and functions listed under Lisp formulas in Tables: list, string, number and control forms, regular expressions on strings, defun, pcase, cl-loop, the seq- and cl- sequence functions, time functions, princ and message. Like emacs -Q --batch, it uses lexical binding, with dynamic binding for variables declared with defvar, and the syntax table of Emacs Lisp mode for regular expressions and capitalize. A quoted lambda, '(lambda ...), runs with dynamic binding, as in Emacs. A closure can be called, stored and passed to functions such as mapcar; a block that takes one apart as a list, compares it or prints it needs Emacs. It has no buffers. A block that uses something the interpreter does not have fails with "This block uses Emacs Lisp that runs only in Emacs, on the Mac." A Lisp error fails the run, as it does in Emacs.

In the Mac App Store version, Emacs Lisp blocks run in the same interpreter as on iOS. A block that uses something it does not have fails with "This block uses Emacs Lisp that runs only in Emacs."

Variables are bound with let around the body. :results output collects what the block prints with princ, prin1, print and terpri.

calc blocks

A calc block runs as ob-calc runs it in emacs -Q, with orgstar's Calc, the one table formulas use. Each line of the body is trimmed and handled in turn; blank lines are skipped:

  • A line that is the name of a :var puts its value on the stack.
  • A line that starts with ' runs a stack key on the stack: '+, '-, '*, '/, '^, '% (modulo), '\ (integer division), 'n (negate), '& (inverse), 'Q (square root) and 'A (absolute value).
  • Any other line is a formula. Its value goes on the stack; if it isn't a number, the formula is evaluated again with the block's variables put in, and that goes on the stack as text, as ob-calc does.

The result is the top of the stack, shown with Calc's own settings in emacs -Q: 12 significant digits, all of them shown (1/3 gives 0.333333333333). A vector is written as a table row and a matrix as a table, unless :results asks for a string. :prologue and :epilogue add lines before and after the body.

Each run starts with an empty stack. In Emacs the Calculator's stack carries over from one block to the next, so a block that relies on what an earlier block left there gives a different result in orgstar.

:var values can be numbers, and lists and tables of integers; a table of one row is a vector. Errors that Emacs reports, such as "Too few elements on stack" or a stack key on a formula ("Invalid data object encountered"), fail the run without writing a result.

What orgstar's Calc doesn't do as Emacs's Calc does is refused rather than given a different result: functions and forms table formulas also refuse, Calc's constants such as pi and e (which Emacs replaces by their values), stack keys other than those above, dates, string variables, variables named like Calc's constants (e, pi, i) or with characters other than letters and digits, lists with fractional numbers, and a :prologue or :epilogue that is a bare number. The message is "This calc block can't be calculated here:" with the reason. The download version then runs the block in emacs -Q --batch when Emacs is installed.

sqlite blocks

A sqlite block runs as ob-sqlite runs it: the body goes to sqlite3 on standard input, with the options the header arguments name, and the output becomes the result. The download version runs sqlite3 (macOS has one in /usr/bin) and uses the SQLite library only when it isn't installed. The Mac App Store version and iOS run the block in the SQLite library, writing the output as macOS's sqlite3 writes it.

Header argumentEffect
:db fileThe database, relative to the file's folder or :dir; without it, an in-memory one
:readonly yesOpens the database read-only
:csv, :list, :column, :html, :lineThe output mode; without one or :separator, csv
:separator s, :nullvalue sThe column separator and the text for NULL, in list mode
:colnames yesThe first row of the result becomes the table's header
:header, :echo, :bailPass -header, -echo and -bail to sqlite3

As in Emacs, a mode option resets the header, separator and NULL text to that mode's, so :header has an effect only with :separator alone.

:var values replace $name in the body, in any case. A table becomes a CSV file and $name its path, for .import:

#+begin_src sqlite :var t=prices :db shop.db
create table if not exists prices(item text, price real);
.import --csv $t prices
select item, price * 2 from prices;
#+end_src

The output is read as a table the way ob-sqlite reads it, with org-table-convert-region; a single value becomes a scalar. Where that conversion fails in Emacs, as it does for output whose last line is empty in a mode other than csv, the run fails with the same message. In csv mode sqlite3 ends lines with CR LF and Emacs keeps the CR, so the last column of each row ends with a CR, which shows as ^M; orgstar writes the same.

In the Mac App Store version, :db must be in a folder orgstar has access to: a folder in the sidebar, or one you granted access to.

Without sqlite3, these dot-commands run: .headers (.header), .mode with list, csv, column, html or line, .separator and .nullvalue with one plain argument, and .import FILE TABLE (with --csv or not) into a table that exists, of rows that fit it. Anything else is refused with "This sqlite block can't run here:" and the reason: other dot-commands, header values with characters the shell would read differently (spaces, quotes, ~, ;, |), BLOB values, control characters other than tab and newline in values, text other than ASCII or values on several lines in column mode and in line mode's column names, EXPLAIN statements, text that isn't UTF-8, and :echo unless the result is text (:results output, for example). When the refused value comes after other statements, those statements have already run, and the message says so.

Graphics

dot (Graphviz), plantuml and mermaid blocks draw a picture into :file, and the result is a link to it. :file is required: "language code blocks need a :file header argument". The file's extension picks the output format; with none, png is used.

LanguageCommand
dotdot -T/ext/ -o file
plantumlplantuml -p -t/ext/, output to the file
mermaidmmdc -i input -o file

A plantuml body without an @start… line is wrapped in @startuml and @enduml. :cmdline adds options to the command. plantuml must be installed and on the PATH described under Languages that run.

Without dot or mmdc, and in the Mac App Store version and on iOS, orgstar draws dot and mermaid blocks itself, with Graphviz and mermaid built in:

  • It writes SVG and PNG files. Another extension fails with "language blocks draw only SVG and PNG files in this version of orgstar."
  • :cmdline may hold -K/engine/ for dot, and -t /theme/ (--theme) and -b /color/ (--backgroundColor) for mermaid. Anything else fails with "language blocks with this :cmdline don't run in this version of orgstar."
  • A PNG has the size the picture has at 96 dots per inch, on white unless -b says otherwise; a mermaid diagram wider than 800 points is scaled down to that, as mmdc does.
  • Mermaid labels are drawn as SVG text, not HTML, so line breaks and Markdown in labels can look different from mmdc's.
  • The picture comes from the same Graphviz and mermaid code as the programs use, in the versions orgstar ships (Viz.js 3.31.0 and mermaid 12.3.0), so it can differ in detail from an installed program of another version or with other fonts.
#+begin_src dot :file graph.svg
digraph { a -> b }
#+end_src

#+RESULTS:
[[file:graph.svg]]

Writing the files

  • A file whose contents would not change is left alone, so its modification time stays the same.
  • A read-only file is replaced.
  • Tangling into the Org file itself is refused: "Not allowed to tangle into the same file as self".
  • When a file's mode, from :shebang or :tangle-mode, can't be set, the other files are still written and their modes set, and the message area says "Tangled N code blocks from file, but can't set the mode of path: reason".

What tangling refuses

Tangling stops, writes nothing and says why when:

  • :var refers to a source block, which would have to run: "would run a block while tangling".
  • A noweb reference runs a block, <<name()>>, in a block whose :noweb expands when tangling: "The noweb reference <<…>> would run a block while tangling, which isn't supported yet; nothing was tangled."
  • A shell block's :var is a table or list.
  • :var is used in a language other than shells, Python, Emacs Lisp, C, C++, D, Java, Fortran and Clojure.
  • A C, C++, D or Fortran block's :var table keeps rules (with :hlines yes), or a value has no type the language takes.
  • A Lisp header value cannot be evaluated: "is Lisp tangling can't evaluate yet; nothing was tangled."
  • :tangle-mode is in a form it does not read.
  • :comments needs a comment syntax it does not know.
